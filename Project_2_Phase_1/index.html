01

The framework and its basic unit

What LangChain is, and what a chain does

When we call an LLM API directly, we send one complete prompt and we get back one reply as plain text. The prompt has to be written out fully each time and the reply has no fixed structure, so the code that receives it has to figure out the meaning on its own.

LangChain is a framework that sits above that API call and provides reusable components for it. The main ones are prompt templates, which are prompts written once with variables inside them, and chains, which join those components into a single unit that can be called repeatedly. A normal chain is prompt template → LLM → output parser. LangChain also makes it easy to switch between different LLM providers, because the model is only one component of the chain, so changing from Gemini to Groq does not require rewriting the rest of the code.

A chain, in simple words, is a sequence of steps connected together and run as one. The syntax used for connecting them is called LCEL (LangChain Expression Language) and it uses the | operator, which passes the output of the left side into the right side, same as a pipe in the terminal.

Direct API call

prompt = f"Write a tagline for {name}."
resp = client.generate(prompt)
print(resp.text)

# full prompt written each time,
# reply comes back as plain text

The same task written as a chain

from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template(
    "Write a tagline for {name}."
)

chain = prompt | llm | StrOutputParser()

chain.invoke({"name": "DevSynt"})
chain.invoke({"name": "Daraz"})   # reused, nothing rewritten

One point which is worth noting is that LangChain is not changing the model in any way. The API call happening underneath is exactly the same. The difference is only that the prompt, the model and the parsing step are now separate components which can be replaced individually.

02

Controlling the input and the output

Prompt templates and output parsers

These two are usually explained together but they are solving two different problems, one on the input side and one on the output side.

A prompt template handles the input. The instruction is written once with placeholders inside curly braces, for example {product_name}, and then different values are passed in whenever the template is used. So instead of keeping many similar prompt strings in the code, there is one template and many different inputs.

An output parser handles the reply. By default an LLM answers in normal free-flowing text, which is easy for a person to read but not reliable for code, because there is no fixed field to read a value from. An output parser instructs the model to answer in a defined structure, mostly JSON, and then converts that reply into a form the code can use directly.

There are different parsers for different needs. StrOutputParser simply returns the text content of the response. JsonOutputParser returns a dictionary, and when it is used together with a Pydantic model, the required fields and their data types are defined in advance and those requirements are included in the instructions sent to the model.

Reply from a plain prompt

"Overall this review is pretty positive!
I'd say around 4 out of 5, although the
customer did complain about how long
the delivery took."

The information is there but the code has to extract it from a sentence, which will fail whenever the wording changes.

Same question with an output parser

class Review(BaseModel):
    sentiment: str = Field(description="positive or negative")
    score: int     = Field(description="1 to 5")
    complaint: str

parser = JsonOutputParser(pydantic_object=Review)
chain  = prompt | llm | parser

result = chain.invoke({"text": review})

# {'sentiment': 'positive', 'score': 4,
#  'complaint': 'slow delivery'}

The value is now read directly as result["score"].

An important detail here is that the parser is working on both sides. It adds the format instructions into the prompt before it is sent, and after the reply comes back it converts that reply into a Python object. It is not only cleaning the output at the end.

03

Context across calls, and access to functions

What memory and tool-calling mean for an LLM app

By default an LLM has no memory and every call is completely independent. If the first question is about the weather in Karachi and the follow up question is "what about Lahore", the second call has no information about the first one, so it cannot understand what is being referred to.

Memory means keeping a record of the conversation so far and sending it back with every new call. So the model is not actually storing anything on its side, the previous messages are being provided to it again each time. Because of this the message history keeps growing, and in longer conversations it has to be trimmed or summarised, otherwise every call becomes heavier.

Tool-calling means giving the LLM access to functions that it can choose to use instead of guessing an answer from what it already knows. This is used for things the model cannot know reliably, like a live exchange rate, a record in our database, or an exact calculation. Every function is described to the model through a tool schema, which contains the name of the function, what it is used for, and the arguments it accepts. Based on the question, the model decides whether a tool is needed, which one to use, and what values to pass into it.

The sequence in which a tool call actually happens is given below:

  1. The user asks a question "What is the weather in Islamabad right now?"
  2. The model returns a tool call it responds with get_weather(city="Islamabad") instead of an answer
  3. The application runs the function this part is normal code, it calls the actual weather API
  4. The result is sent back to the model {"temp_c": 31, "sky": "clear"}
  5. The model gives the final answer "It is 31°C and clear in Islamabad right now."

The important point in this flow is that the model itself never executes the function. It only selects the tool and provides the arguments, the execution is done by our own code, and the model only sees the result once it is passed back to it.

  • chat history
  • tool / function calling

04

Moving from a fixed sequence to a decision

What LangGraph is, and the difference between a chain and an agent

A chain runs a fixed sequence of steps and the order always remains the same. This is suitable when the steps never change. But many tasks require a decision in the middle of the process, for example checking whether the data is clean and sending it for cleaning if it is not, repeating a step when the output fails validation, or skipping a step completely when it is not required.

Such logic can be handled with if conditions around chains up to a certain limit, but after that the code becomes difficult to follow and it is not clear anymore which paths are actually possible in the system.

An agent is different from a chain because it looks at the current situation and decides what to do next, rather than following a route that was already fixed while writing the code. LangGraph is the library used to build these decision-making systems. In LangGraph the application is defined as a graph instead of a straight line, the possible steps and the connections between them are declared first, and which connection is followed is decided at runtime on the basis of the data.

Difference between a chain and an agent
ChainAgent (graph)
The path is fixed at the time of writing the codeThe path is decided at runtime
Runs from start to end once, in orderCan loop back, repeat a step or stop early
Output of one step is passed into the next stepAll the steps share one state which they read and update
Suitable for a predictable taskRequired when the next step depends on the result

  • agent

05

The four core concepts of a graph

Nodes, edges, state and conditional edges

LangGraph is mainly built on four concepts, and everything else is made using these.

Node

One step in the graph. In the code it is a normal Python function which receives the state, performs its work and returns the values it has updated.

Edge

A fixed connection between two nodes, showing what runs next. There is no decision involved in it, the next step is always the same one.

Conditional edge

A decision point. A function checks the state and returns the name of the node which should run next, so the same graph can follow different paths.

State

The shared data which moves through the graph. Every node can read it and add to it, so a later node is able to see what an earlier node has produced.

The diagram below is the small graph I made while practicing this, it checks an order and decides what should happen next depending on whether the item is in stock. It is a simple example but all four concepts are present in it. 

from typing import TypedDict
from langgraph.graph import StateGraph, END

# the state, this data is available to every node
class OrderState(TypedDict):
    order_id: str
    in_stock: bool

# a node, it receives the state and returns what it updated
def check_order(state):
    return {"in_stock": lookup(state["order_id"])}

# the function used by the conditional edge.
# it returns the NAME of the next node, not a result.
def route(state):
    return "ship" if state["in_stock"] else "notify"

g = StateGraph(OrderState)
g.add_node("check", check_order)
g.add_node("ship", ship_it)
g.add_node("notify", notify_customer)

g.set_entry_point("check")
g.add_conditional_edges("check", route)  # decided at runtime
g.add_edge("ship", END)                  # always goes to END
g.add_edge("notify", END)

app = g.compile()
app.invoke({"order_id": "A-1042"})

The main thing to notice in this code is that route() does not perform any work and it does not return data, it returns the name of the next node as a string. This is the actual difference between a normal edge and a conditional edge, one of them is fixed in the code while the other one is the return value of a function.

06

The pattern used in the upcoming project

What an orchestrator agent is, and why our project needs one

An orchestrator agent, which is also called a router or a supervisor, receives a task, works out what type of task it is, and then routes it to the specialised agent which should handle it. In most cases it does not perform the actual work itself. It can be understood like a manager, it does not clean the data or write the report, it decides who will do it, then looks at the result and decides whether any further step is needed.

Every specialised agent is a separate node with one narrow responsibility and its own focused prompt. All of them read from and write to the same shared state, so whatever the cleaning agent produces is already available when the analysis agent runs and the results do not have to be passed manually between them.

While going through the official multi-agent example, the part I traced was how the supervisor decides where each task should be sent. It is the same conditional edge concept explained above, the only difference is that agents are placed on the branches instead of simple functions.

Why this pattern is required in our upcoming project Our orchestrator agent receives raw data and it cannot know in advance what kind of data it has been given. If the data is messy it has to be sent to the cleaning agent first, if it is already clean it can go directly for analysis, and if a step fails then it has to be routed back and attempted again. All of this is decided from the data while the program is running. A chain cannot handle this because in a chain the path is already fixed before anything runs, and this is the reason the project needs LangGraph and not only LangChain.

  • supervisor agent
  • multi-agent system
